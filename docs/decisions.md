# X-Gates Win — журнал решений

Что решили, **почему** и **что пробовали и отвергли**. Дополнять в момент решения/коммита.
Открытые вопросы из `HANDOFF.md` §13 закрыты 2026-10-29 (ответы Elyor).

## 2026-10-29 — ответы на HANDOFF §13

### §13.1 Стек: C# / .NET 10 + WPF (а не Kotlin + Compose Desktop)
- Слово Elyor: «что нативнее для Win 10|11, то и используем».
- **WPF** (.NET 10, встроенная Fluent-тема) — нативный фреймворк Microsoft, без JVM. Проверено фактом на
  Linux-сервере: с `<EnableWindowsTargeting>true</EnableWindowsTargeting>` WPF-проект **собирается здесь**;
  `dotnet publish -r win-x64 --self-contained -p:PublishSingleFile=true` + сжатие → PE32+ GUI exe ≈62 МБ.
- **Отвергнут WinUI 3** (Windows App SDK 1.8): на Linux не собирается — его `XamlCompiler.exe` (net472) →
  `Exec format error`. Любая правка UI требовала бы Windows; выигрыша для этого приложения нет.
- **Отвергнут Kotlin + Compose Desktop** (рекомендация `HANDOFF.md` §5): JVM-рантайм, не нативный вид.
- **Цена (принята):** вся логика Android (~10 тыс. строк Kotlin без UI, UI 4.7 тыс., тесты) переписывается на C#;
  синхронизация с Android — только схема C из `UPSTREAM-SYNC.md` (перенос по смыслу).
  Чтобы перенос фиксов был механическим, **C#-код повторяет Kotlin 1:1**: те же имена классов, функций, полей и
  файлов; пакет `com.picosoft.xrayproxydroid.xray.link` → пространство имён `XGates.Core.Xray.Link`, файл
  `xray/link/VlessParser.kt` → `src/XGates.Core/Xray/Link/VlessParser.cs`. Ключевые комментарии («Пр.N», «почему»)
  переносятся вместе с кодом.

### §13.2 Windows для проверок — отдельный ноутбук Elyor (Windows 10)
- Доступ КК — как Phone Bridge у телефонов: ноутбук держит обратный SSH-туннель на сервер; sshd на ноутбуке
  слушает только `127.0.0.1` (наружу не открыт). GUI, запущенный из SSH-сеанса, на экране не виден → запуск окна и
  скриншоты — через задачу планировщика в интерактивном сеансе пользователя. Настраивает Elyor с ноутбука.

### §13.3 Репозиторий — отдельный `pico-soft/X-Gates-Win`
- Создан **закрытым** (видимость Elyor не называл → минимальная экспозиция). Сделать публичным перед первым релизом
  (обновления качаются из GitHub Releases без токена) — только по слову Elyor.
  **Открыт 2026-10-31 по слову Elyor** («Репозиторий открываем сейчас») — см. раздел от 2026-10-31 в конце.
- История форка Android в нём — не утечка: `pico-soft/X-Gates` публичный.

### §13.4 Имя, иконка, данные
- Имя **«X-Gates Win»**, иконка та же (`art/xrayproxy-logo.png`).
- Данные — **`%LOCALAPPDATA%\X-Gates\`** (не `%APPDATA%` Roaming: замеры и «живые» серверы верны только для сети
  этой машины, в перемещаемом профиле они бы уезжали на другие компьютеры; отдельно от папки программы → обновление
  и удаление программы данные не трогают). Внутри — те же файлы/схемы, что в `filesDir` Android, + `logs\`.

### §13.5 Установщик — MSI per-user, без прав администратора
- WiX `Scope="perUser"` → `%LOCALAPPDATA%\Programs\X-Gates Win\`, без UAC.
- Факт: WiX на Linux не работает («The WiX Toolset only supports Windows») → MSI собирается на Windows
  (ноутбук или GitHub Actions `windows-latest`). WiX v7 к тому же требует принять OSMF EULA (платный взнос для
  коммерческого использования) — **решить с Elyor при упаковке**; запасной вариант — WiX v5 без OSMF.

### §13.6 Подпись обновлений — своя (бесплатно); Authenticode — позже, за деньги
- Без Authenticode Windows не проверяет издателя обновления (на Android это делает ОС по подписи APK). Установщик
  качается каскадом, в т.ч. через чужие зеркала → подмена = запуск чужой программы у всех пользователей.
- Своя пара ключей: закрытый — только на сервере (секреты, вне репо, не выводить), открытый — вшит в приложение.
  Релиз подписывает `update.json` (в нём sha256 установщика); приложение не ставит обновление с неверной подписью.
- Не убирает предупреждение SmartScreen при первой установке из браузера — это только платный Authenticode
  (~$200–500/год). Автообновление из приложения (файл без Mark-of-the-Web) предупреждения не должно давать —
  **проверить на ноутбуке**.

### §13.7 Порты — 10815/10816 по умолчанию
- SOCKS5 `127.0.0.1:10815`, HTTP `127.0.0.1:10816` — те же, что на Android (одинаковые инструкции). Только
  loopback: соседи по сети не подключатся, брандмауэр Windows не спрашивает.
- Добавки Windows-версии: при занятом порте — понятное сообщение (не молчаливый сбой); порт можно сменить в
  настройках (на Android — константы; на ПК конфликтов больше: другие клиенты, резервирования Hyper-V/WSL/Docker).

## 2026-10-29 — как переносим Kotlin-код (принципы порта)

### Имена — как в Kotlin, даже вопреки стилю C#
- Портированный код сохраняет Kotlin-имена **дословно**, включая camelCase у членов (`ServerProfile.address`,
  `VlessParser.parse`, `p with { pingMs = … }` вместо `copy(pingMs = …)`), чтобы diff Kotlin↔C# читался построчно
  и фикс из Android переносился механически. Kotlin `object` → `static class`, верхнеуровневые функции файла
  `X.kt` → `static class XKt` + `using static` (как JVM-имя). Новый Windows-специфичный код — обычный C#-стиль.
- **Отвергнуто:** «идиоматичный» C# (PascalCase, LINQ-переписывание) — каждый будущий перенос фикса превращался бы в
  ручной перевод с риском потерять нюанс.

### Слой совместимости `XGates.Core.Compat` — поведение Android, а не .NET
- Kotlin-парсеры подписок опираются на семантику платформы. Её нельзя заменять «похожими» API .NET — другой набор
  серверов и другие serverKey. Перенесены точные порты:
  - `JavaUri` — `java.net.URI` из **Android libcore** (не JDK): на Android «_» в имени хоста разрешён, `%` между
    `[ ]` во фрагменте не декодируется, иначе устроен разбор IPv4. `System.Uri` — мягче и нормализует.
  - `AndroidBase64` — `android.util.Base64`: пропускает ЛЮБОЙ символ вне алфавита; `Convert.FromBase64String` бросает.
  - `org.json` (`JSONObject/JSONArray/JSONTokener`) — мягкий разбор Android (комментарии, одинарные кавычки,
    hex/octal, хвост после значения) и приведения `optString/optInt`; `System.Text.Json` строже.
  - `JavaUrlDecoder`, `JavaNumbers` (Double.toString/valueOf), `KotlinText` (isBlank/trim/toIntOrNull/trimIndent —
    у Kotlin своё определение пробела: U+001C..U+001F да, U+0085 нет).
- Исходники AOSP для сверки лежат в `tools/golden/aosp/` (Apache 2.0).

### Проверка паритета — golden-эталон с настоящего Kotlin-кода
- `tools/golden/run-golden.sh` гоняет корпус (`tools/golden/corpus`, генератор `make-corpus.py`) через НАСТОЯЩИЕ
  Kotlin-классы во временной копии Android-проекта; `android.util.Base64`/`org.json` в JVM-тестах — заглушки, поэтому
  подкладываются реальные AOSP-классы отдельным jar. C#-тест `GoldenParityTests` требует совпадения профилей и
  конфигов xray **байт в байт**. Разово сверено на 905 реальных ссылках 5 дефолтных подписок — 0 расхождений
  (реальный корпус в репо не кладётся: в нём рабочие пароли публичных серверов).
- Ограничение: эталон снимается на JDK 21, а не на телефоне → Android-правки URI проверяются отдельными тестами
  (`AndroidCompatTests`) по исходникам AOSP.
- **Найдено в Android (не чинили в одностороннем порядке, см. UPSTREAM-SYNC):** (1) `JsonConfigParser` отдаёт
  `network="splithttp"`, а `XrayConfigBuilder` его не принимает («unsupported transport») — такие JSON-серверы не
  собираются; (2) ~1.5% реальных vmess-ссылок вида `vmess://<base64>=?…` отбрасываются (хвост после паддинга ломает
  android Base64). Решать вместе с Android-версией.

## 2026-10-29 — ядро xray на Windows: процесс вместо libv2ray

- **Шов — тот же API, что у gomobile-библиотеки Android** (`XGates.Core.Libv2ray`: `Libv2ray.newCoreController`,
  `CoreController.startLoop/stopLoop/isRunning/queryStats`, `Libv2ray.measureOutboundDelay/checkVersionX`), но поверх
  дочернего процесса `xray.exe`. Почему: Kotlin-код, работающий с ядром (XrayController, ServerSpeedTester,
  ServerTester), переносится без смены логики. Логика `measureOutboundDelay` взята из исходников AndroidLibXrayLite
  **Lib v39** (коммит b213898 = версия AAR в Android): 2 GET по keep-alive, минимум, ≤12 с, 200/204.
- **Конфиг — через stdin** (`xray run -c stdin:`): UUID/пароли серверов не пишутся на диск.
- **Статистика**: вывод `XrayConfigBuilder` не трогаем (паритет); `CoreController` при наличии `"stats"` дописывает
  `"api": {listen 127.0.0.1:<эфемерный>, StatsService}`; чтение-со-сбросом — gRPC `GetStats{reset:true}` (свой
  мини-клиент h2c, без NuGet). Отвергнуто: запуск `xray api statsquery` на каждый опрос (процесс раз в секунду).
- **Сироты**: Windows Job Object `KILL_ON_JOB_CLOSE` — ОС убивает xray.exe при любой смерти приложения.
- **Готовность**: строка ядра «core: Xray … started» (печатается после старта inbound-слушателей) или выход процесса
  → ошибка с хвостом вывода ядра (напр. «address already in use»).
- **Версия ядра** — v26.7.28, как в Android; `tools/xray/fetch-xray.sh` (sha256 закреплены в скрипте),
  `third_party/` в git не кладём. **`wintun.dll` из Windows-архива НЕ поставляем** (TUN запрещён рамками продукта).
- Факты xray v26.7.28, найденные тестами: freedom по умолчанию не пускает на loopback/частные IP (`finalRules`);
  у vless-outbound счётчик uplink всегда 0 (через собственный CLI ядра тоже) — то же ядро на Android → паритет.
- ЛОЖНАЯ ТРЕВОГА (2026-10-30, снято): через HTTP-вход xray в режиме пересылки ответ с ПУСТЫМ телом (204, 200 с
  Content-Length: 0) «зависал» — но только с самописным тестовым сервером LocalTestNet. С настоящим HTTP/1.1-источником
  (Python http.server, keep-alive) 204 и пустой 200 проходят через HTTP-вход за ~2 мс, как напрямую и через SOCKS.
  Ядро ни при чём; тесты через HTTP-вход используют ответы с телом.

## 2026-10-29 — потоки: семантика JVM, а не .NET

- В Java/Kotlin необработанное исключение в `Thread { }` убивает ТОЛЬКО этот поток; в .NET — ВЕСЬ процесс.
  Android-код (сторожа батчей, финишёры, посев) написан под JVM. Поэтому все фоновые потоки портированного кода —
  через `KThread.start` (ловит и логирует), пулы — через `FixedThreadPool` (семантика `Executors.newFixedThreadPool`:
  shutdown/shutdownNow/awaitTermination; `Long.MAX_VALUE` = «вечно»). Найдено тестом: краш тест-хоста от
  переполнения TimeSpan в фоновом потоке.
- Уточнение (порт CrashReporter): «убивает только поток» — это голая JVM. На Android системный обработчик по
  умолчанию роняет ВЕСЬ процесс, а CrashReporter перед этим пишет отчёт; сервис потом поднимает START_STICKY.
  На Windows оставляем процесс жить (перезапускать трей-приложение некому — пользователь молча остался бы без
  прокси), но **отчёт о сбое пишем** (`KThread.onUncaught` → `CrashReporter.report`), иначе ошибка в поле невидима.
  Отвергнуто: ронять процесс «как на Android» — без перезапуска это хуже для пользователя.

## Найдено в Android-коде при порте (решение Elyor 2026-10-30: чинить в ОБЕИХ версиях)

Порт держал паритет, поэтому Windows-версия повторяла эти места. **Решение Elyor (2026-10-30): исправить здесь, а
Android-КК получает хэндофф** (`docs/android-handoff/`) с теми же исправлениями в виде Kotlin-патчей. Патчи
проверены здесь же на временной копии Android-кода: golden-эталон (`tools/golden`, `GOLDEN_SRC=<копия с патчами>`)
снят с ПАТЧЕННОГО Kotlin, и C# с ним совпадает — паритет сохраняется, пока Android не примет патчи.
1. `JsonConfigParser` отдаёт `network="splithttp"`, а `XrayConfigBuilder` его не принимает («unsupported transport»)
   → JSON-серверы со splithttp не собираются. **ИСПРАВЛЕНО:** splithttp — синоним xhttp в `XrayConfigBuilder`
   (как raw→tcp, kcp→mkcp); профиль не меняется (serverKey стабилен). Патч Android — `patches/0001`.
2. ~1.5% реальных vmess-ссылок вида `vmess://<base64>=?…` отбрасываются (хвост после паддинга ломает Base64).
   **ИСПРАВЛЕНО:** Base64 декодируется до «?» (хвост не нужен — имя в "ps"); ссылки с ? и & (vmess-std) по-прежнему
   откладываются. Корпус golden пополнен двумя такими ссылками. Патч Android — `patches/0002`.
3. `NetworkMonitor.rebuildAndRateTop`: `coerceIn(targetTop, needMeasure.size)` при `needMeasure < 10` — пустой
   диапазон → IllegalArgumentException → «Ошибка фон-рейтинга топа», фон-рейтинг ничего не мерит (малые пулы).
   **ИСПРАВЛЕНО:** нижняя граница `min(targetTop, size)`. Тест `BackgroundRatingTests` (живой монитор, 3 сервера)
   до правки падал этой ошибкой, после — топ обновлён, оба кандидата измерены. Патч Android — `patches/0003`.
4. `ServerSpeedTester.fetchViaTempInstance`: исключение `startLoop` не ловится → обрывает ВЕСЬ каскад загрузки
   подписки, а не только этого кандидата (ступень 6). **ИСПРАВЛЕНО:** catch → null (провал одного кандидата).
   Тест: битый ключ reality (ядро не стартует) первым, живой сервер вторым — до правки исключение наружу, после —
   каскад пробует обоих, тело получено через второго. Патч Android — `patches/0004`.
5. `XrayController.start`: проверка `isRunning` и запуск не атомарны с `stop()` в `runCoreStart` — два почти
   одновременных `XrayProxyService.start` (полный тест: «первый рабочий» → «точный топ») теоретически могут оставить
   поднятым НЕ последний выбранный сервер, хотя ProxyState покажет последний. **ИСПРАВЛЕНО:** операции с ядром
   (старт/стоп/пауза/возобновление/восстановление) берут номер в момент запроса и выполняются под одной блокировкой,
   только если всё ещё последние. Попутно закрыта родственная гонка: старт сразу перед «Стоп» поднимал ядро ПОСЛЕ
   стопа. Тест `CoreStartRaceTests` (тестовая задержка в окне гонки) до правки — оба сценария неверны, после — верны.
   Патч Android — `patches/0005`.
6. `Sanitizer` (отчёт о сбое): маска «токенов» `[A-Za-z0-9+/=_\-]{24,}` съедает имена исключений от 24 символов
   (`IllegalArgumentException`, `ConcurrentModificationException`, …) и длинные имена методов в трассировке —
   отчёт теряет главное: ЧТО упало. **ИСПРАВЛЕНО:** слово только из латинских букв не маскируется; ключи, hex и
   base64 с цифрами/+/=_- — как раньше (тесты Sanitizer в обоих языках). Патч Android — `patches/0006`.
7. `UpdateInstaller.download`: если на ВСЕХ адресах файл скачался, но SHA-256 не совпал, а свой прокси не запущен —
   пользователю показывается «Прямой доступ к GitHub заблокирован, а прокси не запущен…» вместо «контрольная сумма
   не совпала» (ветка `!isOwnProxyUp()` перекрывает `lastFail`). Подсказка ложная: файл дошёл, но не тот.
   **ИСПРАВЛЕНО:** если хоть один адрес отдал файл с неверной суммой — CHECKSUM_MISMATCH с деталями; подсказка про
   прокси — только когда файл не дошёл вовсе. Патч Android — `patches/0007`.
8. «Не использовать» (`onRemoveCurrent`): сервер ставится на паузу и запускается полный тест, но
   `FullTestRunner` берёт АКТИВНЫЙ сервер «в норме» инкумбентом, не проверяя паузу → переключится, только если
   кандидат в `keepBestMultiplier` раз быстрее. Итог: кнопка «Не использовать» на рабочем сервере часто ничего не
   переключает: туннель остаётся на нём, и в «Живых» он виден как подтверждённый активный (с пометкой паузы).
   Найдено тестом модели «Главной». **ИСПРАВЛЕНО:** отложенный активный не инкумбент — тест подключает лучший
   разрешённый кандидат (нет рабочих — туннель остаётся). Патч Android — `patches/0008`.
9. `buildDiscriminators` (подпись одноимённых серверов): «гарантия уникальности» — последние 4 символа serverKey,
   но ключ кончается пустыми полями (`…|tcp||||||`) → у одноимённых серверов с одинаковыми протоколом/транспортом
   подпись одинаковая «… · ||||», строки неотличимы. **ИСПРАВЛЕНО:** совпала подпись → + адрес:порт (IPv6 в скобках);
   совпал и он → + «#» и 4 hex от String.hashCode ключа (стабильно, одинаково с Android). Патч Android — `patches/0009`.
   Все 9 патчей вместе на копии Android (4b0bebb): юнит-тесты 37/37, `assembleDebug` собирается (2026-10-31).

## 2026-10-29 — обновления на Windows

- Источник: свой репозиторий `pico-soft/X-Gates-Win` (§13.3), вложения релиза — `update.json`, `update.json.sig`,
  `XGatesWin-<версия>-win-x64.msi`. В update.json поле `abi` = `"win-x64"`, `packageName` = `com.picosoft.xgates.win`
  (своё значение — чтобы Android-релиз никогда не приняли за Windows-обновление и наоборот: проверка 121.C).
- Подлинность (§13.6): на Android её даёт ОС (подпись APK обязана совпасть с установленной). На Windows без
  Authenticode такого нет, поэтому **update.json подписан нашим ключом ECDSA P-256** (встроено в .NET — без
  зависимостей); в update.json — SHA-256 установщика, так что подпись закрывает и файл. Без подписи или с неверной
  подписью обновление НЕ предлагается вовсе (а не «предлагается с предупреждением»).
  Отвергнуто: Authenticode-сертификат (платный, ежегодно — решение Elyor, можно добавить позже поверх);
  GPG/minisign (лишняя зависимость в приложении); только SHA-256 из API GitHub (подменяется вместе с релизом).
- Ключ: закрытый — только на сервере разработки `~/.local/share/x-gates-win/update-signing/` (700/600), вне git;
  открытый — в `UpdateSignature.cs`. Потеря закрытого ключа = установленные копии больше не примут обновление

## 2026-10-29 — порты локального прокси (§13.7)

- По умолчанию 10815/10816 (как Android). Меняются в настройках; хранятся в ОТДЕЛЬНОМ `win_settings.json`
  (`WinSettingsStore`), а не в `settings.json` — тот остаётся байт в байт совместим с Android (StoreCompatTests).
  `XrayConfig.SOCKS_PORT/HTTP_PORT` стали свойствами (читаются на момент использования, как дефолты Kotlin), так
  что новый порт сразу видят конфиг ядра, каскад загрузки, внешний IP, замеры активного туннеля.
- Проверка пары: 1024–65535 и разные; неверная пара не сохраняется, испорченный файл → дефолты (прокси должен
  подняться, а не молча не стартовать).
- Занятый ЧУЖОЙ программой порт: перед подъёмом ядра пробная привязка 127.0.0.1:порт (без SO_EXCLUSIVEADDRUSE —
  как привязывается само ядро, иначе ложные «занят» из-за TIME_WAIT прежнего туннеля). Занят → в статусе
  «Порт N занят другой программой — закройте её или смените порт в «Настройки → Локальный прокси»» вместо
  безликого «ядро не запустилось».
- Автозапуск при входе в Windows в `win_settings.json` НЕ хранится: источник правды — сам реестр (HKCU Run),
  иначе флажок разойдётся с фактом (пользователь мог удалить запись через «Автозагрузку» диспетчера задач).

## 2026-10-30 — окно (WPF) и как его проверять без Windows

- Логика экранов — в `src/XGates.App` (net10.0, без WPF): порт состояния и обработчиков composable-экранов
  MainActivity.kt под теми же именами (MainScreenModel = BootScreen, SubscriptionsModel, BlocklistModel,
  AppBootstrap = XrayApp+onCreate/onResume). Тестируется на Linux с настоящим xray. WPF (`src/XGates.Win`) только
  рисует снимки моделей и пробрасывает события Windows. Отвергнуто: логика в code-behind (здесь не проверить).
- «Главный поток» модели — интерфейс `IUiThread` (WPF: Dispatcher; тесты: свой однопоточный исполнитель) — та же
  дисциплина, что `runOnUiThread` + mutableStateOf в Compose.
- Окно: закрытие = в трей (прокси работает, как сервис Android); «Выход» — меню трея (ядро останавливается).
  Один экземпляр на пользователя (мьютекс + событие «покажи окно»; повторный запуск выводит окно). `--autostart`
  (запись HKCU Run, только по флажку) = BootReceiver: поднять последний сервер без полного теста, окно не показывать.
  Перерисовка — таймером ≤4 раз/с, списки обновляются на месте (пересоздание теряло клики — находка ревью).
- Уведомления Android → значок в трее: статус = подсказка значка, остальное — всплывающие подсказки.
- Chrome/Edge берут только системный прокси, а его не трогаем → в «Настройках» инструкция: Firefox (ручной SOCKS5
  + DNS через прокси), Chrome/Edge (расширение или ярлык с `--proxy-server`), Telegram Desktop. Отвергнуто без
  Elyor: кнопка «запустить Chrome через прокси» (это уже новая функция, решать ему).
- Установщик: WiX v5 (MS-RL, бесплатно), `Scope="perUserOrMachine"` (WiX сам ставит ALLUSERS=2 и
  MSIINSTALLPERUSER=1 → `%LOCALAPPDATA%\Programs\X-Gates Win`, без UAC). Явное свойство MSIINSTALLPERUSER =
  дубль символа → `wix build` падает (найдено ревью по исходникам WiX 5.0.2). Запись автозапуска при удалении
  остаётся, если флажок был включён (MSI не трогает значение Run) — известное ограничение.
- Проверка: окно, трей и MSI здесь НЕ запускались (нет Windows, Wine нет и не показателен). Заготовлены
  `tools/ci/windows.yml` (ручной запуск: тесты на Windows, запуск окна + скриншоты UIA, MSI
  собрать/поставить/удалить; лежит вне `.github/workflows`, т.к. токен без права `workflow` — включается
  копированием) и `tools/windows/check.ps1` + `docs/windows-check.md` (чек-лист для ноутбука) — всё в ветке
  `wip/windows-shell` (отправлена в origin как резервная копия). Независимое ревью кода окна (агент) нашло 4 реальных дефекта — исправлены там же.

## 2026-10-30 — факты монитора на настоящих обрывах (тесты OutageRecoveryTests)

- Обрыв активного сервера → монитор сам переключает на живой (проверено). Время до переключения по умолчанию —
  до ~2–2,5 мин, и это ЗАМЫСЕЛ Android-кода, не порта: при здоровой связи полная проверка не чаще
  `connectionCheckIntervalSec` (60 с; досрочные пробуждения дебаунсятся ради батареи), затем grace 90 с
  (перепроверка каждые 25 с), затем лестница. Ускорить можно ползунком «Проверка связи» (до 30 с); grace — константа.
  На Windows батарея ноутбука тоже есть, так что дебаунс уместен; решать про другие значения — Elyor.
- **Решение Elyor 2026-10-30: редкая проверка — только на батарее; на шнуре — как можно чаще, «лишь бы не
  перегружать процессор».** Сделано: на шнуре (стационарный ПК — всегда) проверка здоровой связи раз в 10 с, обрыв
  объявляется после 30 с тишины (перепроверка 10 с). Факт: от обрыва до переключения 34 с (два прогона
  `AcPowerChecksTests`, боевые значения, монитор не будили) вместо 2–2,5 мин. Цена проверки без трафика: старт
  временного xray ≈ 0,03–0,04 с CPU (замер на этом сервере) и ~3 КБ; с трафиком пользователя пинга нет вовсе.
  Grace укорочен с согласия Elyor: он не про батарею, а против ложных обрывов — сервер, замолчавший на 30–90 с,
  теперь заменяется. Экономия трафика и мобильная сеть — как на батарее (там важнее трафик). Ползунок «Проверка
  связи» теперь действует только на батарее. **Отход от паритета с Android** (там решение не принималось).
- Пропал прямой канал → «Нет интернета», ядро не трогается; вернулся → тот же сервер подтверждён (проверено).
- Все серверы мертвы → «Рабочих серверов нет» + предложение включить выключенные источники (проверено).
- Находка №3 (coerceIn при пуле < 10) воспроизводится в живом сценарии: «Ошибка фон-рейтинга топа — Cannot coerce
  value to an empty range: maximum 0 is less than minimum 10». (Исправлено позже — см. №3 выше.)

## 2026-10-31 — что ядро реально шлёт: фрагментация, allowInsecure, extra

Elyor спросил, интересна ли маскировка из соседнего Rust-проекта (свой ClientHello, фрагментация, HTTP/2 под Chrome).
Ответ дал замер: локальный приёмник на петле, ядро v26.7.28, скрипт разовый.

- **ClientHello уже как у Chrome**, даже без `fp` в ссылке: uTLS, GREASE, X25519MLKEM768, ALPS, ECH-GREASE, порядок
  расширений случайный на каждое соединение. Сверка по составу: живого Chrome на сервере нет.
- **HTTP/2 у XHTTP — отпечаток Go** (`SETTINGS 2=0,4=4194304,5=16384,6=10485760`, `WINDOW_UPDATE 1073741824`), сосед прав.
  **Отвергнуто** подгонять под Chrome: кадры идут внутри TLS, ТСПУ их не видит. tls.peet.ws видит только потому, что сам
  завершает TLS. Цена — форк ядра.
- **Свой Rust-клиент и системный туннель отвергнуты:** TUN запрещён рамками продукта, остальное ядро уже умеет.
- **Фрагментация ClientHello — опция, выключена по умолчанию** (Elyor: «да, делай оба»). Через `freedom` + `sockopt.dialerProxy`,
  параметры обычные для клиентов Xray. `finalmask` в ядре тоже умеет дробить, но выбран уже замеренный путь. Польза против
  настоящей блокировки здесь не проверяема: помогает только при блокировке по SNI и добавляет около 0,15 с. Настройка в
  `WinSettings`, чтобы не трогать `settings.json`; канал загрузки XHTTP наследовать `sockopt` не умеет, ставим явно.
- **`allowInsecure` больше не пишем:** ядро отвергает конфиг с `true`, сервер выглядел мёртвым. Отвергнуто: подставлять
  вместо него что-то, отключающее проверку, — ядро убрало это намеренно. Читаем замену, `pcs` и `vcn`. Негодный pin
  выбрасываем: без него сертификат проверяется как обычно, а с ним ядро отвергает весь конфиг.
- **`extra` только через список разрешённых полей** (`XhttpExtra`): это данные подписки, а в `StreamConfig` есть
  `masterKeyLog` (запись файла), `certificates` (чтение файлов), `sockopt`. Запрет отдельных имён не годится: Go сравнивает
  имена без учёта регистра. `downloadSettings` без адреса конфиг проходит, а ядро падает на первом соединении: такую ссылку
  отбрасываем. Список сверять при каждом обновлении ядра.
- **Грабли тестов:** самоподписанному приёмнику нужен `pinnedPeerCertSha256`, не `allowInsecure`; ядро повторяет
  подключение, поэтому на каждый замер кусков нужен свой приёмник, иначе в очереди лежит прошлая попытка.
